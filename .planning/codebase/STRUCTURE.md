## 2. Directory Purposes

- **`backend/`** — the entire Motoko canister. Flat module-per-concern layout (no subpackages except
  `authorization/`). This is intentional: Motoko projects in this repo favor a small number of large,
  flat `.mo` files imported directly by the two actor entrypoints rather than deep package trees.
- **`frontend/src/components/`** — organized by *feature area* (`farm/`, `pools/`, `season/`, `social/`,
  `sports/`, `market/`), with a shared `ui/` for design-system primitives and `layout/`/`effects/` for
  cross-cutting chrome. A handful of components live at `components/` top level (`LoginButton.tsx`,
  `PlanningBoard.tsx`, `ProcurementModal.tsx`) because they're used across multiple feature areas or
  don't cleanly belong to one — this is the existing precedent for cross-cutting components.
- **`frontend/src/hooks/`** — one hook per backend "domain" (farm, auction, market prices), each wrapping
  React Query around one or more `backendActor` calls. This is the mandatory integration point between
  UI and canister — components must not call `backendActor` directly.
- **`frontend/src/declarations/`** and **`src/declarations/`** — both are dfx-generated output
  directories. `dfx.json` configures `backend`'s declarations `output` to `frontend/src/declarations`,
  which is the one actually imported by app code (`@/declarations/...`). `src/declarations/` appears to
  hold generated bindings for `frontend`/`internet_identity` canisters from an earlier/parallel dfx
  config — treat it as generated/legacy, verify against current `dfx.json` before relying on it, and
  never hand-edit either.
- **`docs/game-design/`** — treat this as the specification source of truth for gameplay rules, economy
  formulas, UI/design system, and backend architectural constraints (dual-entrypoint rules live here).
  When backend or frontend behavior conflicts with a doc here, prefer investigating which is stale rather
  than assuming the doc is wrong.
- **`docs/archive/`** — historical agent plans/backlogs/reviews; informative for context but not
  authoritative for current behavior.
- **`execution/tests/`** — shell-script black-box tests that exercise a running dfx replica via `dfx canister call`
  (integration/E2E style), named per feature/phase (e.g. `test_phase8_auctions.sh`, `test_organic_workflow.sh`).
  This is the primary backend test surface in this repo (no Motoko unit-test framework is wired in).
- **`frontend/src/__tests__/`** — Vitest-based frontend tests (`vitest.config.ts` at `frontend/` root).
- **`scripts/`** — repo-level operational scripts for starting the local replica, running tests, verifying UI.
- **`.github/workflows/`** — the only two CI/CD entry points; playground deploy is push-triggered and
  automatic, mainnet deploy is manual and confirmation-gated (see ARCHITECTURE.md §3/§6).

## 4. Naming Conventions Observed

- **Motoko files**: `snake_case.mo` for logic modules (`game_logic.mo`, `auction_logic.mo`,
  `hiring_logic.mo`), suffixed `_logic` for anything implementing gameplay rules. `types.mo` is the sole
  exception (no suffix) since it holds only type definitions. The `authorization/` subfolder uses
  `kebab-case.mo` for `access-control.mo` (inconsistent with the rest — note this if adding new auth files,
  match `access-control.mo`'s existing kebab-case rather than introducing a third style).
- **Motoko identifiers**: `PascalCase` for types/variants (`PlayerFarm`, `GameError`, `#NotFound`),
  `camelCase` for functions and stable vars (`getPlayerFarm`, `stablePlayerFarms`). Stable-serialization
  helper vars are consistently prefixed `stable` + PascalCase field name (`stablePlayerFarms`,
  `stableSaturation`, `stableGlobalSeason`).
- **React components**: `PascalCase.tsx`, one component per file, file name matches the exported
  component (`FarmGrid.tsx` exports `FarmGrid`). Modal components live under a feature folder's `modals/`
  subdirectory (`components/farm/modals/PlantingModal.tsx`).
  Component-scoped CSS uses a matching `.css` file alongside the component (`AuctionDashboard.css`,
  `RivalCard.css`) — the exception rather than the rule; most styling is Tailwind utility classes inline.
- **Hooks**: `useX.ts` in `frontend/src/hooks/`, one hook per backend domain, exporting both the hook and
  its React Query key constants (`FARM_QUERY_KEY`, `MARKET_STATE_QUERY_KEY`,
  `ACTIVE_CONTRACTS_QUERY_KEY`) so other hooks/components can `invalidateQueries` against them.
- **Contexts**: split across two directories by convention — `context/` (singular) holds `AuthContext.tsx`,
  `contexts/` (plural) holds `AudioContext.tsx`. This is an existing inconsistency in the repo, not a
  typo to "fix" silently — a new cross-cutting context should probably go in `contexts/` (plural) to
  match the majority/newer pattern, but check with whoever owns `context/` before consolidating.
- **Config constants**: `frontend/src/config/*Constants.ts`, `SCREAMING_SNAKE_CASE` for exported constant
  objects (`PHASE_DESCRIPTIONS`, `SOUNDS`), `PascalCase` type aliases (`SeasonPhase`, `GameAction`).
- **Shell test scripts**: `execution/tests/test_<feature_or_phase>.sh`, e.g. `test_phase8_auctions.sh`,
  `test_seasonal_harvest.sh` — named after either the game phase/milestone or the feature under test.

## 5. Where to Add New Code

- **New gameplay mechanic (backend)**: add a new `backend/<feature>_logic.mo` module (snake_case,
  `_logic` suffix) with pure-ish functions operating on explicit state/params. Wire it into **both**
  `backend/main.mo` and `backend/main_mainnet.mo` — add the `import`, any new `stable var` (with matching
  `preupgrade`/`postupgrade` serialization in both files), and the new `public shared`/`public query`
  function in both entrypoints identically. Add corresponding types to `backend/types.mo`. Add an
  `execution/tests/test_<feature>.sh` script exercising it end-to-end against the local replica. If the
  mechanic has an economy/balance dimension, add or update the relevant spec under
  `docs/game-design/economy/`.
- **New frontend feature/tab**: add a `frontend/src/components/<feature>/` directory following the
  existing feature-folder pattern (see `pools/`, `season/`). Add a `useX.ts` hook in
  `frontend/src/hooks/` if it needs backend data, exporting a query-key constant. Register the new tab
  in `frontend/src/App.tsx`'s `activeTab` union and the tab-switch JSX, and add any nav entry to
  `frontend/src/components/layout/Sidebar.tsx`.
- **New Candid-facing backend function**: define it in the appropriate `*_logic.mo`, expose it via a
  `public shared`/`public query` wrapper in both `main.mo` and `main_mainnet.mo`, then regenerate
  bindings (`dfx generate`) so `frontend/src/declarations/` picks up the new method on `_SERVICE` before
  wiring a hook to it.
- **New reusable UI primitive**: `frontend/src/components/ui/` (matches the existing shadcn/radix-based
  primitives already there — `button.tsx`, `dialog.tsx`, `card.tsx`, etc.).
- **New auth/session behavior**: changes belong in `frontend/src/context/AuthContext.tsx`. Preserve the
  documented invariant that `isAuthenticated` is set only after `backendActor` is ready (see
  ARCHITECTURE.md §5) — do not add a code path that flips `isAuthenticated` true before `backendActor`
  is set without an explicit, reviewed exception (the existing `initTestMode` exception reverts on
  failure and is clearly commented).
- **New RBAC role/permission**: `backend/authorization/access-control.mo` + `MixinAuthorization.mo`,
  mirrored identically in both entrypoints' wiring block.
- **New game-design spec/decision**: `docs/game-design/<economy|gameplay|ui|backend|lore>/<topic>.md` —
  keep specs here rather than in `docs/archive/` (archive is for superseded/historical material only).
- **New integration test**: `execution/tests/test_<name>.sh` for backend/dfx-level tests;
  `frontend/src/__tests__/<name>.test.ts(x)` (Vitest) for frontend unit/integration tests.

## 6. Special / Generated Directories

- `frontend/dist/` — **generated** Vite production build; this is what `dfx.json`'s `frontend` canister
  serves. Never hand-edit; regenerated by the frontend build step.
- `frontend/src/declarations/` — **generated** by `dfx generate` from whichever `.mo` entrypoint was
  built (`main.mo` for local/playground per `dfx.json`). Never hand-edit; regenerate after any backend
  interface change.
- `src/declarations/` — **generated**, appears to be an older/parallel declarations output (covers
  `frontend` and `internet_identity` canisters) not aligned with the current `dfx.json`'s single
  `backend` declarations output path; verify which declarations set is actually consumed before trusting
  it, and prefer `frontend/src/declarations/` for anything imported by app code.
- `.dfx/` — **generated** local replica state/build artifacts; not meaningful to hand-edit or rely on
  for architecture decisions.
- `docs/game-design/` — **source-of-truth specs**, not generated, but authoritative over ad hoc comments
  in code when the two disagree — treat conflicts as a signal to investigate which side has drifted
  (see the Track B EOP-syntax drift noted in ARCHITECTURE.md §3 as a live example).
- `docs/archive/` — historical only; do not treat as current design authority.
- `.github/workflows/.gitkeep` — placeholder, no functional content.
