<task type="checkpoint:decision" gate="blocking">
  <decision>How should a player runner-up's trickle credit be carried from global auction resolution to the player's own payout?</decision>
  <context>
Plan 03-03 credited an AI runner-up directly inside `_performGlobalAuctionResolution`, because `aiCompetitors` is writable right there. The player path cannot work the same way: `resolveSeasonAuctions` reads the caller's farm into a local `farm` binding *before* it calls `_performGlobalAuctionResolution`, and writes `playerFarms.put(caller, updatedFarm)` from that snapshot afterwards — so anything the global pass writes to the caller's farm is silently overwritten. The credit therefore has to be recorded somewhere the caller's own loop can read.

CLAUDE.md makes this **Ask First**: "Changing the shape of stable state (`stable var`, the `Farm` record, `Infrastructure`). On ICP a bad upgrade loses player data irreversibly." `stableAuctionContracts` is a `stable var` (`backend/main.mo:3007`) and `AuctionContract` is also part of the Candid surface, so Option A below is a persisted-schema change on a live data path. D-05 locked the payout *formula*; it did not choose the mechanism, and the planner is not the right party to choose it silently.
  </context>
  <options>
    <option id="option-a">
      <name>Add optional fields to the existing AuctionContract record</name>
      <pros>Perfectly symmetric with the existing `winnerPlayerId` / `winnerBidPLN` optional fields; the player loop reads `c.runnerUpPlayerId == ?callerText` as a one-line mirror of the winner loop it sits beside; all contract state stays in one record; the `#Fulfilled` status transition already guarantees once-only payment.</pros>
      <cons>Changes the shape of a `stable var` element type, which is the exact surface CLAUDE.md flags — a rejected upgrade on an existing canister is a data-loss event. `AuctionContract` is Candid-visible, so it also requires `dfx generate backend` and a committed `frontend/src/declarations/` update guarded by `candidContract.test.ts`. There is no precedent in this repo for adding a field to an already-persisted record.</cons>
    </option>
    <option id="option-b">
      <name>New stable var side-table of runner-up credits</name>
      <pros>Follows this repo's own established, already-shipped pattern: `stable var stableClubOwnership : [(Text, Text, Nat)]` (backend/main.mo, Phase 2 SPORTS-01/02/03) carries a comment stating "Adding this `stable var` is additive — existing farms upgrade with an empty ownership list and see every club as unclaimed, which is correct." A brand-new stable var takes its initializer on upgrade, so no existing record shape changes and no existing persisted value can be misread. No Candid change, no `dfx generate`, no declarations churn.</cons>
      <cons>Contract-related state now lives in two places, and the entry must be explicitly consumed (filtered out) after payment to guarantee once-only semantics, rather than riding the contract's existing `#Fulfilled` transition. One more stable var to reason about at upgrade time.</cons>
    </option>
    <option id="option-c">
      <name>Credit the player immediately during global resolution, persist nothing new</name>
      <pros>No new persisted state at all; smallest diff.</pros>
      <cons>Actively unsafe as the code stands: `resolveSeasonAuctions` writes the caller's farm from a snapshot taken before the global pass, so a credit written during that pass is overwritten for the one caller most likely to be the runner-up. Fixing that means re-reading the farm after `_performGlobalAuctionResolution`, which changes the transaction shape of an existing method for a bugfix phase. Recorded so the option is visibly considered, not recommended.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. Option B is the planner's recommendation on the strength of the in-repo `stableClubOwnership` precedent, but this is a persisted-state decision and it is the user's call.</resume-signal>
