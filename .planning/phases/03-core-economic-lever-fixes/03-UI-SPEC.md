## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps inside the fertilizer-type picker rows |
| sm | 8px | `DropdownMenuRadioItem` vertical padding (matches existing `dropdown-menu.tsx` default `py-1.5`≈6px→round to 8px grid usage elsewhere), compact badge spacing |
| md | 16px | Default spacing inside the new Regional Output card, dropdown content padding |
| lg | 24px | Section padding (unchanged — SellModal/CompetitorsPanel already use `p-4`/`p-6`) |
| xl | 32px | Layout gaps between the three CompetitorsPanel summary tiles (unchanged, existing `gap-4`≈16px is what's actually there — do not silently change existing spacing while touching one tile's content) |
| 2xl | 48px | Not used by this phase's new elements |
| 3xl | 64px | Not used by this phase's new elements |

**Exceptions:**
- The existing icon-only action buttons that trigger fertilize (`ParcelCard.tsx:312-320`, `h-8 w-8` = 32px) are **below the 44px touch-target minimum**. This is pre-existing to the codebase (shared by every other parcel action button — water, prune, harvest) and out of scope for Phase 3; touch-target sizing across parcel actions belongs to Phase 9 (UX-03/UX-04). **The new fertilizer-type dropdown trigger must reuse this existing 32px button as-is** — do not resize it as an unplanned side effect of adding the picker.
- The `ImperialOrchard.tsx` radial-menu fertilize button is `w-14 h-14` (56px) — already compliant, no exception needed there.

## Typography

**Known pre-existing exception, not touched by this phase:** `SellModal.tsx`'s hero numbers (Unit Price, Total Revenue) render at `text-3xl` (30px) and the dialog title at `text-2xl font-light` (300 weight) — both outside this 2-weight, 4-size contract. This is pre-existing token debt (`.planning/STATE.md`); this phase's Boy Scout scope is the season-price *row* only, not a re-theme of the whole modal's typography. Do not expand scope to "fix" these while wiring the season term.

## Color

The codebase currently has **two co-existing, internally-consistent local palette conventions** (this is the measured reality per `.planning/STATE.md`'s design-token-debt note, not a preference): a generic Tailwind slate-dark theme (`SellModal.tsx`, `CompetitorsPanel.tsx`) and the brass/hull Neo-Steampunk tokens (`BidModal.tsx`, `RivalCard.tsx`, orchard components). **Rule for this phase: new elements match the local convention of the file they land in.** Do not introduce a third palette, and do not re-theme either file wholesale — that is Phase 9 (UX) territory, not a 7-bugfix economy phase.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0f172a` (Tailwind `slate-900`) | Background/surface for `SellModal.tsx` and `CompetitorsPanel.tsx` — unchanged, already the established convention in both files receiving this phase's new content |
| Secondary (30%) | `#1e293b` (`slate-800`, used as `border-slate-800`) / `bg-slate-900/50` | Card and section-panel surfaces inside those same two files — the fertilizer-type dropdown's `DropdownMenuContent` should sit on `bg-popover` (already mapped to the same dark family via `--popover` CSS var) with a `border-slate-800`-equivalent border to match its host |
| Accent (10%) | `#f59e0b` (Tailwind `amber-500`) | **Reserved for:** the selected/active fertilizer-type indicator in the dropdown (radio-checked state), positive season-multiplier values (already the convention at `SellModal.tsx:229` — `emerald-400` for >1, see note below), the "High Demand" badge family already present. Do **not** use amber for the Regional Output tile's icon/value — see Destructive note below for why that tile uses a neutral, not accent, treatment. |
| Destructive | `#f43f5e` (Tailwind `rose-500`) | **Reserved for:** negative season-multiplier values (mirrors the existing `rose-400` convention at `SellModal.tsx:229` for <1), the "Fertilizing Failed" error toast, "Market Saturated" warning badge (pre-existing, unchanged) |

**Footnote — BidModal/RivalCard local convention (unchanged by this phase, since ECON-07 adds no UI):** dominant `.mechanical-hull` charcoal gradient (`#1a1510`→`#121212`), secondary `rgba(0,0,0,0.4-0.5)` panels with `border-[#d4af37]/20-30`, accent `#d4af37` brass, destructive `red-900/500` (the "Retract" button). Recorded here only so the checker has the full picture if it inspects `BidModal.tsx` — no change is being made there.

**Correction to the existing code, not a color decision:** `SellModal.tsx:229`'s season-row color logic (`pricingFactors.seasonMod > 1 ? emerald-400 : < 1 ? rose-400 : slate-400`) is **already correct and already built** — the fix is wiring `seasonMod` to a real backend-mirrored value, not touching this color logic at all.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (fertilizer picker) | Each dropdown item's action is the CTA itself — no separate confirm step, matching the existing single-click-per-action convention already used by every other parcel action (water/prune/harvest fire immediately on click). Item label pattern: **"Fertilize with {Type Name}"** (e.g., placeholder "Fertilize with Standard NPK" / "Fertilize with Organic Compost" — **final type names are an economy-balance decision, not yet locked; see `03-RESEARCH.md` Open Question 1 / Assumption A1-A2.** The picker's *shape* — a 2-3 item radio list, each with a one-line tradeoff caption — is locked regardless of which naming option wins.) |
| Empty state | Not applicable this phase. The fertilizer-type list is a small fixed local constant (never fetched, never empty). `CompetitorsPanel.tsx` cannot render zero competitors — `competitor_logic.mo` hardcodes exactly 3 AI archetypes (Marek/Kasia/Hans) that always exist. |
| Error state | **"Fertilizing Failed"** / body = the canister's own rejection reason string, e.g. *"Fertilizing Failed — {reason}. Try again once the issue is resolved."* Reuses the exact toast pattern already established in `App.tsx`'s `handleParcelAction` ("Action Restricted" / `variant: "destructive"`) — do not invent a new toast style for this one action. |
| Destructive confirmation | Not applicable this phase. No delete/irreversible UI action is introduced — fertilizing, selling, and viewing competitor/rival data are all standard reversible gameplay actions already gated by the existing phase-restriction toast. |

**ECON-07: no UI-SPEC content, and why.** Confirmed by direct read this session (`backend/competitor_logic.mo:54-109`): there are and always will be **exactly 3** AI archetypes (Marek "The Traditionalist", Kasia "The Eco-Visionary", Hans "The Aggressor"), and `BidModal.tsx`'s `RivalryDeck` **already renders the correct canonical names** — `RivalCard name="Marek"`, `"Kasia"`, `"Hans"` are already right, matching `03-RESEARCH.md`'s "naming only" framing exactly. The existing 3-slot `RivalCard` layout is therefore already correct and needs **no visual adjustment** for "possibly more numerous or dynamic states" — there is no such risk; the count is fixed by backend code, not data. The remaining ECON-07 work (`frontend/src/lib/gddTemplate.ts`'s `Jan Kowalski`/`Anna Nowak`/`Piotr Wiśniewski` → `Marek`/`Kasia`/`Hans`) touches **zero rendered UI** — `gddTemplate.ts` is never imported by any `.tsx` file (confirmed by grep this session), it is a reference/template text file. A design contract for it would be meaningless.

**Flagged, not fixed, not in scope (per CLAUDE.md's "never paper over a known defect" — surfaced, not silently expanded):** `BidModal.tsx`'s `RivalryDeck` hardcodes each rival's `status` prop (`Marek="outbidding"`, `Kasia="idle"`, `Hans="active"`) regardless of any real bid data — this is decorative, not live, for every contract shown. ECON-07's requirement text is naming-consistency only ("pick one canonical scheme"), not live-status wiring, so this phase does not fix it. If the team wants rival status to reflect real bidding, that needs a new requirement (RivalCard's `RivalStatus` type — `'idle' | 'active' | 'outbidding' | 'defeated'` — is already rich enough to carry real data; only the source of the `status` prop would need to change).
