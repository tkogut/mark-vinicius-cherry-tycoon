<objective>
Give the fertilizer-type parameter a real effect: validate it against a closed set, persist which type was applied to a parcel, and let Synthetic-Intensive raise that parcel's yield potential by 5%.

Purpose: `fertilizeParcel` has accepted a `Text` fertilizer type since it was written and thrown it away, behind a comment promising a future enhancement. There is no fertilizer-type system anywhere in the game — no taxonomy, no UI, no persisted state — so this is a design gap, not a wiring gap. D-01 locked the taxonomy and the magnitude; this plan builds the backend half and its mirror, and plan 03-07 builds the picker that feeds it.

Output: a validated three-type taxonomy, a persisted per-parcel type, a new multiplicative term in the yield formula, a TS mirror pinned by the parity oracle, and an upgrade proven over real parcel data.
</objective>

Plan 03-04 faced a structurally identical choice for the runner-up credit — **read `03-04-SUMMARY.md` first and say whether you are following the same option or diverging, and why.** Consistency across the two is worth something; a reflexive copy without re-checking the specifics is not.
  </context>

      <name>Add an optional field to the existing CherryParcel record</name>
      <pros>Reads naturally: the parcel remembers what it was fed, directly beside the `lastFertilized` season number it already remembers. `calculateYieldPotential`'s signature does not change, so neither does its only other caller (`game_logic.mo`'s cost estimator) nor the shape of the TS mirror.
