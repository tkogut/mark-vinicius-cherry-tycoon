## Warnings

### WR-01: Vacuous assertion in "fee identical whether sourced from volumeKg or requiredVolumeKg" test

**File:** `frontend/src/__tests__/preSeasonFutureIntegrity.test.ts:568-574`
**Issue:** This test claims to verify that ECON-09's fee is computed
identically regardless of whether it's "sourced from volumeKg or from
contract.requiredVolumeKg" — i.e., it reads as a regression guard for the
exact bug ECON-09 fixed (fee computed from the wrong variable). But both
`feeFromVolumeKg` and `feeFromRequiredVolumeKg` are computed with the
*identical* call: `refCalcCommitmentFee(refCalcLockedPrice(6), 10_000)`. There
is no second code path that actually sources the fee from a caller-supplied
`volumeKg` distinct from `requiredVolumeKg` — `refCalcCommitmentFee` doesn't
know or care which variable name the caller used. The assertion
`feeFromVolumeKg === feeFromRequiredVolumeKg` is therefore true by
construction (a pure function called twice with the same arguments), and
would still pass even if `commitPreSeasonFuture`'s real fee call reverted to
`AuctionLogic.calcCommitmentFee(lockedPrice, volumeKg)` (the pre-fix,
exploitable version) — this test cannot detect that regression. (In this
suite that specific regression *is* caught elsewhere — the source-drift guard
at lines 388-391 asserts the literal text
`calcCommitmentFee(lockedPrice, contract.requiredVolumeKg)` appears in
`main.mo` — but this test's own name and stated purpose is not backed by what
it actually checks, and a future edit to the source-drift guard could quietly
weaken that protection while this test kept passing and looking like independent coverage.)
**Fix:** Either delete the test (the source-drift guard already covers the
regression it claims to guard against), or rewrite it to actually exercise two
different inputs, e.g.:
```ts
it('the fee uses requiredVolumeKg even when a caller-supplied volumeKg differs (post-fix: the guard rejects mismatches, but if it were bypassed the fee must still be sourced from requiredVolumeKg, not volumeKg)', () => {
    const requiredVolumeKg = 10_000;
    const maliciousVolumeKg = 1; // what the pre-fix exploit supplied
    const lockedPricePLN = refCalcLockedPrice(6);

    const feeFromRequiredVolumeKg = refCalcCommitmentFee(lockedPricePLN, requiredVolumeKg);
    const feeFromMaliciousVolumeKg = refCalcCommitmentFee(lockedPricePLN, maliciousVolumeKg);

    expect(feeFromRequiredVolumeKg).toBe(5_000);
    expect(feeFromMaliciousVolumeKg).toBe(0); // the exploit's own truncation
    expect(feeFromRequiredVolumeKg).not.toBe(feeFromMaliciousVolumeKg);
});
```

## Info

### IN-01: Guard's `else 0` branch is provably unreachable at its one call site

**File:** `backend/main.mo:3512`
**Issue:** `remainingForPSF := if (remainingForPSF >= deliveredKg)
remainingForPSF - deliveredKg else 0;` is correctly guarded, but at its only
call site `deliveredKg` is always defined as `if (remainingForPSF >=
c.requiredVolumeKg) c.requiredVolumeKg else remainingForPSF` (line 3501) —
which makes `remainingForPSF >= deliveredKg` true in both branches (equal in
the second). The `else 0` arm can never execute given the current call site.
This is not a bug — it's consistent with the codebase's existing "guard every
Nat subtraction" convention used elsewhere in the same function (e.g. lines
3430, 3432, 3507) — but it's worth naming so a future refactor that
decouples `deliveredKg`'s derivation from this guard doesn't mistake the
`else 0` arm for dead, removable code; it is the only thing that would protect
against underflow if that coupling were ever broken.
**Fix:** No action required. Optionally add a one-line comment noting the
invariant (`deliveredKg <= remainingForPSF` always holds here) so the guard's
purpose as a structural invariant, not just defensive boilerplate, is explicit
to future editors.

### IN-02: Two additional tests document intent more than they prove it

**File:** `frontend/src/__tests__/preSeasonFutureIntegrity.test.ts:201-207` and `:184-199`
**Issue:** "iteration order is the array order and is deterministic" (201-207)
asserts that calling a pure JS function twice with the same input produces the
same output — true of any pure function and not specific to
`refResolvePSFContracts`'s actual iteration-order semantics. "a second
player's #Awarded PSF interleaved in the array is skipped by the caller
guard" (184-199) is a real and useful test (it does exercise the
`committedByPlayer` filter with a genuinely different array), so it is not
flagged as a Warning; the 201-207 test alongside it is weaker but at least
doesn't claim to guard against a specific named regression the way WR-01
does, so it's noted here rather than raised to Warning.
**Fix:** Optional. If kept, consider merging it into the "reordering" test
(209-223), which does exercise a genuinely different input ordering and
therefore says something the pure-function determinism check does not.
