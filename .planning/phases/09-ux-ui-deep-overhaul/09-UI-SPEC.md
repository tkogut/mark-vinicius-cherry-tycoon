# Phase 9 — UX/UI Deep Overhaul — UI Design Contract

> Visual and interaction contract for Phase 9's remaining open items. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this document.** Per the orchestrator's routing, this contract covers the three requirements that introduce or restyle actual visual surface: **UX-02** (orchard lighting/atmosphere overlay), **UX-03** (Bar Meter / Metric Badge stat grammar, incl. the D-11/D-12 dead-control and fake-gauge fixes it drags in), and **UX-06/UX-09** (building placement + the new Action Dock). **UX-05** (Processing Plant wholesale bonus) is a backend formula + numeric mirror change with zero UI/copy change — `Marketplace.tsx`'s card copy is already correct per `09-RESEARCH.md`, so it has no section below. **UX-08** (machine phase gating) is a boolean-condition change on already-rendered entities with no new visual element, so it also has no section below beyond the cross-reference in Building Slots (they share the ownership-gating pattern). UX-04 (sidebar guest-state fix) is a state-branching fix, not a new visual pattern — its one required copy string is in the Copywriting Contract below, following the exact `SportsCenter.tsx` pattern `09-RESEARCH.md` names as the reference implementation.

All decisions below are either **locked** (cite the `D-xx` from `09-CONTEXT.md`) or **derived defaults** (marked `[default]`, consistent with locked decisions and existing repo conventions, confirmable by the checker/planner rather than re-asked of the user).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--charcoal` `#121212` / `--background` `hsl(20 10% 6%)` | Page background, orchard canvas soil/backdrop, Action Dock's outer shell |
| Secondary (30%) | `--card` `hsl(25 12% 10%)` family, realized via the existing `.mechanical-hull` / `.mahogany-plate` classes | Action Dock content panels, Sidebar, Marketplace cards, BidModal shell |
| Accent (10%) | `--brass-primary` `#C9A84C` (Tailwind `brass` `#d4af37`) | See "Accent reserved for" below |
| Destructive | `--ruby-harvest` `#8B1A1A` (Tailwind `ruby` `#9b111e`) | Destructive/critical-only, see below |

**Accent (brass/gold) reserved for — exhaustive list, nothing else may use it:**
1. The Action Dock's primary CTA button (wired "View Market Auction" per D-11, and any building "Upgrade" CTA per D-10)
2. Metric Badge icon glyph + primary numeral (Treasury, Prestige)
3. Bar Meter fill in its **neutral/progress** state only — the season/phase-cycle meter, which has no "good/bad" semantic, always renders brass regardless of position
4. Building-slot hover/selection outline when a building is clickable (D-10's affordance that it opens the Action Dock)
5. The active/selected item indicator in `Sidebar.tsx` (already existing convention, unchanged by this phase)

**Destructive (ruby) reserved for — exhaustive list:**
1. Bar Meter fill in its **critical** threshold state (machine wear >80% of the 200% cap `MAINT-02` already defines; storage/cold-storage fill ≥95%)
2. Error-state copy/icon accents (e.g. a failed auction-data fetch in the migrated BidModal)
3. Negative-delta indicator in a Metric Badge (a per-turn cash/prestige loss)

**Third, narrowly-scoped token — not a new hex, reused exactly as `design-tokens.md` already names it:** `--emerald-glow` `rgba(80, 200, 120, 0.8)`, documented there as "Resource gauges, vacuum tubes." This phase keeps that exact, pre-existing reservation for **one** use only: **Bar Meter fill in its nominal/healthy state** (storage <80% full, wear <50% of cap). This is not a fourth CTA-hierarchy color — it never appears on a button, icon, or badge, only as a meter fill — so it does not violate the 60/30/10 chrome hierarchy above, which governs interactive/structural color, not data-driven fill state. Apply via `bg-[var(--emerald-glow)]` (Tailwind arbitrary-value referencing the existing CSS custom property) or an inline `style`, never a Tailwind default shade (`bg-emerald-500`, `bg-green-500`) and never a new hex literal — this is exactly the 1018-hardcoded-shade debt `.planning/STATE.md` flags, and Phase 9 is explicitly the corrective pass, not another contributor to it.

## Component Contracts

### A. Orchard Lighting Overlay (UX-02 — D-01, D-02, D-03)

**What ships:** a two-layer, always-visible atmospheric overlay embedded directly inside `ImperialOrchard.tsx`'s render tree (not a portal, not `fixed inset-0` — container-relative, per `09-RESEARCH.md` Pitfall 3), replacing the deleted `GoldenHarvesterView.tsx`'s cinematic-modal version of the same effect.

1. **God Rays layer** — reuse the existing `.god-ray-45` CSS utility (`frontend/src/index.css:351-361`) as-is: `absolute`, `pointer-events-none`, `mix-blend-overlay`, pure CSS gradient + `transform`/`opacity` keyframe animation (no `backdrop-filter`, no canvas — cheapest possible option and already D-00-compliant). Size it to the orchard's own container (`inset-0` of the orchard wrapper), not the viewport.
2. **Golden Pollen layer** — reuse `ParticleLayer` (`frontend/src/components/effects/ParticleLayer.tsx`) with `preset="GoldenPollen"`, adapted to size its canvas to the orchard container (`ResizeObserver` on the parent, not `window.innerWidth/innerHeight`).

**Intensity formula (D-02 — always visible, Golden Harvester only scales it):**
```
intensity = clamp(0.35 + goldenHarvesterLevel * 0.12, 0.35, 1.0)
```
Level 0 (unowned) → 0.35 (visible baseline, satisfies "always visible for every player"). Each level adds 0.12, saturating at 1.0 around level 5+. This is a `[default]` formula — the exact coefficients are a one-line tuning constant, not a locked balance number (D-03 marks this reversible/pure-rendering).

**Performance degradation (D-03):**
- **Mobile:** `useMediaQuery('(max-width: 768px)')` (existing hook, existing breakpoint convention from `Sidebar.tsx`) → halve the computed `intensity` value before passing it to `ParticleLayer` (mobile intensity = `intensity * 0.5`), never disable the God Rays CSS layer (it's nearly free).
- **Low framerate:** sample a rolling average frame delta inside the particle layer's own `requestAnimationFrame` loop (no shared FPS utility exists — `09-RESEARCH.md` Pitfall 3 confirms this must be self-contained). If the rolling average exceeds ~33ms/frame (<30fps) for more than 1 second, halve `intensity` again (compounds with the mobile halving, floor at a minimum of 0.1 so the effect never fully vanishes — D-02 forbids gating visibility to zero).
- **z-index:** overlay sits **above** the tree/path/building canvas layer (so light appears to fall on the scene) but **below** the Action Dock and any modal (`z-index` lower than the Action Dock's fixed-bottom chrome) — solid panels must never be seen through the pollen/rays layer, per D-00's "solid panel backgrounds" principle.

### B. Bar Meter (UX-03 — D-04)

**Base primitive:** shadcn `Progress` (`frontend/src/components/ui/progress.tsx`) — already the correct reference implementation in `ParcelDetailsPanel.tsx` and `CompetitorsPanel.tsx`. Do not build a new bar component.

**Standardized dimensions (this phase's normalization — currently mixed `h-1.5`/`h-2` across the two reference sites):**
- Track height: **`h-2` (8px)** everywhere a Bar Meter appears (machine wear, storage fill, season progress, BidModal's migrated gauges). One size, not per-context.
- Track background: `bg-[var(--charcoal-light)]` equivalent — use the Tailwind `charcoal.light` (`#1e1e1e`) token already registered in `tailwind.config.js` (`bg-charcoal-light`), **not** `bg-slate-800`/`bg-slate-900/20` (the current hardcoded-shade instances in `ParcelDetailsPanel.tsx`/`CompetitorsPanel.tsx` — migrate them to the token when touched, per the Boy Scout rule in `.planning/STATE.md`'s design-token-debt note, though only the components this phase's plan actually opens are required to change).
- Label: micro-label typography row above or beside the bar (12px/400/1.2), e.g. `WEAR` / `STORAGE` / `PHASE PROGRESS`, uppercase, `tracking-wide` (matches existing `.hull-header`-adjacent micro-label convention already seen in `MainDashboard.tsx`'s `Phase`/`Treasury` captions).

**Fill color — three-state semantic, tokens only (no new hex):**

| Bar Meter use | Nominal (emerald-glow) | Warning (copper) | Critical (ruby) |
|---|---|---|---|
| Machine wear (`MAINT-01`/`MAINT-02`'s wear-vs-200%-cap model) | 0–50% of cap | 50–80% of cap | >80% of cap |
| Storage / cold-storage fill | 0–79% | 80–94% | ≥95% |
| Season/phase-cycle progress | **always brass** (`--brass-primary`) — no semantic threshold; this is a neutral progress indicator, not a health/danger value |

Copper warning state uses `--copper-dormant` `#B87333` (Tailwind `copper` `#b87333`) — already a declared token, not new.

**Where this replaces existing gauges:**
- `MainDashboard.tsx`'s "Reserves" and "Organic" `EmeraldGauge` instances → Bar Meter, storage-fill thresholds above. **Flagged, not silently fixed** (see "Flagged Defects" below): both source values currently add an unexplained flat `+15`/`+5` padding on top of the real percentage before display — that is a data-accuracy question, not a visual-grammar one, and this UI-SPEC does not mandate removing it, only migrating its visual presentation.
- `BidModal.tsx`'s three `EmeraldGauge` instances (D-12) → Bar Meter. "Harvest" and "Storage" have real bounded backend-equivalent data available (`CherryParcel.quality`/average parcel quality for "Harvest"→ rename to **"Avg. Quality"**; the same storage-fill ratio `MainDashboard.tsx` already computes, minus its padding bug, for "Storage"). **"Morale" has no real backend equivalent anywhere in this codebase** (confirmed — no morale/labor-satisfaction field exists in `Types.PlayerFarm` or `AuctionContract`). Per D-12's "wire to real data, don't fabricate," the planner must either (a) repurpose the slot to a real bounded field (e.g. average parcel `fertility%`, already used elsewhere as a legitimate 0–100 value) or (b) drop to a 2-meter layout. **Do not invent a new backend field or keep a hardcoded 95 just to preserve visual symmetry.**

### C. Metric Badge (UX-03 — D-04)

**Composition** (icon + number + delta, no bar — for open-ended values only: cash, prestige):
```
[lucide icon, 16px, brass] [number, 20px/600 semibold, brass, tabular-nums] [delta, 12px/400, emerald-glow if positive / ruby if negative / muted-foreground if zero]
```
- Base container: extend the existing `Badge` component (`frontend/src/components/ui/badge.tsx`)'s `cva` variants with one new variant (e.g. `variant="brass"`: `border-brass/40 bg-charcoal-light text-foreground`) rather than hand-rolling a parallel component — consistent with "Don't Hand-Roll" from `09-RESEARCH.md`.
- Delta format: `+1,250 PLN` / `−3 pts` (sign always shown, `PLN` suffix per `UX-11`'s existing money-formatting ratchet — never a literal `$`).
- No percentage/fraction is ever shown on a Metric Badge — that is exactly the shape D-04 reserves for Bar Meter. If a value needs a defined ceiling to be meaningful, it is a Bar Meter, not a Metric Badge; if it's genuinely open-ended (cash has no cap, prestige has no cap), it is a Metric Badge.

**Where this applies:** `MainDashboard.tsx`'s current plain-text "Phase"/"Treasury" diagnostic blocks migrate to this — Treasury becomes a real Metric Badge (cash + per-season delta if available from the existing seasonal report data), Phase becomes a Bar Meter (it's bounded — phase-cycle progress, not a badge) per table B above, not a badge.

### D. MainDashboard.tsx → Action Dock migration (D-00, D-11)

`MainDashboard.tsx` is confirmed (`09-RESEARCH.md`) to already be the app's de facto bottom-dock location — this phase formalizes it into D-00's single consolidated **Action Dock**, rather than building a new panel elsewhere.

**Structural requirements:**
1. **Solid backgrounds only** — remove `bg-black/60 backdrop-blur-xl`, `bg-white/5`, `bg-black/40 backdrop-blur-sm` (all present in the current file) in favor of the existing solid `.mechanical-hull` / `.mahogany-plate` classes already used for the outer shell. This is a direct, in-scope fix: D-00's "no expensive transparency forcing background re-render" principle is being actively violated in the exact file UX-03 is rewriting.
2. **Three-zone layout preserved** (left Diagnostics / center CTA / right Reserves), each zone re-skinned to the new grammar:
   - Left: Metric Badge for Treasury (was plain text), Bar Meter for phase-cycle progress (was plain text "Phase" label — now shows progress toward the next phase transition, not just the phase name; the phase *name* remains as the Bar Meter's label).
   - Center: the CTA button, wired to real navigation per D-11 (see Copywriting Contract) — the "STEAM PRESSURE" `ImperialDial` is **removed entirely** (D-11: fix or remove; no real "steam pressure" metric exists anywhere in the game's data model, so remove rather than fabricate a binding). This also naturally resolves `09-RESEARCH.md`'s Open Question 1 — the removal happens as a stated consequence of D-04's grammar replacing this panel, not a silent byproduct.
   - Right: two Bar Meters (Reserves, Organic) per table B's storage-fill thresholds.
3. **Selected-building content mode (D-10):** when a building slot is clicked in the orchard, the *same* Action Dock's center/relevant zone swaps to show that building's name (16px/600 semibold heading), a wear/condition Bar Meter, and the "Upgrade Building" CTA — **not** a new floating panel, **not** a modal. A small dismiss affordance (an "×" or clicking the building again) returns the dock to its default farm-HUD content. This is the Smart-UI "contextual overlay instead of a blind modal" principle from D-00 applied literally: one dock, two content modes, driven by selection state.

### E. Building Slots in the Orchard (UX-06/UX-09 — D-06, D-07, D-08, D-09, D-13)

**The four building types and their fixed slot order** (D-13 requires a fixed, type-keyed order; this contract sets it, matching `Marketplace.tsx`'s own declared card order for cross-screen consistency — a player who buys top-to-bottom in the Marketplace sees the same left-to-right order appear on the parcel's N/NE edge):

| Slot | Building type | Rationale |
|---|---|---|
| 1 (northmost) | `Warehouse` | First storage-tier purchase in Marketplace's own listing order |
| 2 | `ColdStorage` | Grouped visually next to Warehouse — both are storage buildings |
| 3 | `ProcessingFacility` | The UX-05-adjacent building; sits after the storage pair |
| 4 (northeast-most) | `SocialFacilities` | Last in Marketplace's listing order |

Render **nothing** for an unowned type's slot (matches the existing `orchardAutomationConfig?.hasX` convention of "nothing appears unless the player has opted in" — no vacant-lot placeholder art, since none exists and D-06 has no drag-and-drop discovery need to hint at).

**Facing/placement rationale (D-07, preserved verbatim per the user's own reasoning — do not lose this when implementing):** *"Wszystkie wygenerowane assety... mają rzut 3/4 skierowany fasadą i drzwiami w stronę South-West... stałe sloty budowlane muszą znajdować się wyłącznie na północnej / północno-wschodniej krawędzi... Zapobiegnie to również zasłanianiu sadu przez wysokie dachy budynków."* — the sprites face South-West, so North/North-East slots make their fronts face into the farm, and keep tall rooflines from occluding the tree canopy.

**Seasonal sprite switching (D-08):** reuse `buildingSpriteFolder()`/`seasonKeyFromBackend()`/`BUILDING_SPRITE_SEASONS` exactly as `Marketplace.tsx` already implements them — extract to a shared `frontend/src/lib/buildingSprites.ts` module per `09-RESEARCH.md`'s "Don't Hand-Roll" guidance, import from both call sites. No new art, no new season-key spelling.

**Z-index (D-09) — exact formula, extending the existing continuous-projected-Y rule:**
```typescript
// Existing pattern (ImperialOrchard.tsx:1202-1214): soil=0, building=+1, tree=+2, machine=+4, worker=+5
zIndex: s * 100000 + Math.round(y * 10) + 1   // typeOffset = 1, between soil and tree
```
North-edge tiles already project to a smaller `y` than interior/path tiles, so painter's-algorithm ordering draws buildings first (underneath) in the common case — the `+1` offset only breaks ties at genuinely equal `y` values, it does not carry the entire "render below trees" requirement alone (per `09-RESEARCH.md` Pattern 1's note).

**Click behavior (D-10):** clicking a rendered building slot does not open a modal — it sets the Action Dock's selection state to that building, per Component Contract D above. Hover state gets the brass outline treatment listed under "Accent reserved for" item 4.

## Flagged Defects Found During Research (out of this phase's locked scope — recorded per CLAUDE.md's "never paper over a known defect you happen to touch")

1. **`MainDashboard.tsx`'s `storagePercentage`/`organicPercentage` padding bug.** `Math.min(100, Math.max(0, (totalCherries / 50000) * 100)) + 15` and the analogous `+ 5` for organic — both add a flat, unexplained bonus on top of the real ratio *before* clamping to 100, meaning the displayed fill is never accurate even before considering the `EmeraldGauge`→Bar Meter migration. Not named in `09-CONTEXT.md`'s D-01..D-13 or `09-RESEARCH.md`'s Common Pitfalls. This UI-SPEC does not mandate a fix (it's a data-accuracy/logic question, not a visual-grammar one) but the planner should decide explicitly whether to carry the `+15`/`+5` forward into the new Bar Meter or strip it, rather than silently porting a bug into the new component.
2. **Font token drift.** `docs/game-design/design-tokens.md` documents `Cinzel`/`Inter` as the app's fonts; neither is actually loaded. Noted in the Design System table above; not fixed this phase (out of D-00..D-13's scope, and adding a webfont has its own performance/FOUC considerations that deserve their own decision, not a drive-by fix).
3. **`BidModal.tsx`'s "Morale" gauge has no real backend equivalent** — see UI Considerations' unresolved row above.
